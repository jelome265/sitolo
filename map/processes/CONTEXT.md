# Processes

One job: route an agent to real repository movements that actually execute or are demonstrably followed.

## Inputs

| Source | File/Location | Section/Scope | Why |
|---|---|---|---|
| Process cards | process cards in this folder | Selected movement | Change-impact reasoning |
| Schema | ../_meta/schema.md | Full file | Process semantics |

## Process

1. Select a real executable movement affected by the requested change.
2. Read Input → Movement → Output.
3. Follow linked object cards.
4. Re-check the authoritative source before implementation.
5. Keep target-state or unwired flows in governing documents, not in this process shelf.

## Outputs

| Artifact | Location | Format |
|---|---|---|
| Process card | [slug].md | Markdown |

## Conformance rule

A process card must describe a movement that actually executes or is actually followed in the current repository. Future or ghost processes belong in project contracts and implementation status documents until executable evidence exists.
