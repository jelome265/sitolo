# Sitolo — Upgrade, Expansion & Tier Migration Model

**Status:** Commercial packaging/control document  
**Date:** 2026-09-22

---

## 1. Principle

Customers upgrade because their business becomes more complex.

```BUSINESS GROWS
→ CONTROL NEED GROWS
→ SITolo CAPABILITY GROWS
```

Not:

```FEATURE BLOCK
→ PAY OR STOP
```

---

## 2. Complexity Dimensions

Measure:

- locations;
- users;
- catalogue size;
- transaction volume;
- procurement complexity;
- reconciliation workload;
- reporting complexity;
- approval needs;
- integration requirements;
- governance/security requirements.

Exact thresholds are hypotheses until validated.

---

## 3. Tier Model

| Tier | Complexity |
|---|---|
| Duka | one simple operating location |
| SME | small team / basic management |
| Growth | deeper control and workload |
| Multi-Branch | multiple operating locations |
| Enterprise | governed, integrated organization |

---

## 4. Upgrade Triggers

Potential evidence-based triggers:

- second location;
- sustained additional users;
- manager workflows;
- advanced reconciliation;
- advanced procurement;
- central reporting;
- enterprise integration;
- security/procurement requirements.

---

## 5. Progressive Disclosure

A user should see the complexity required for their role.

Example:

```
BRANCH CASHIER
→ simple mobile

HQ FINANCE
→ dense reconciliation

SECURITY ADMIN
→ control-plane policy
```

---

## 6. Plan Recommendation

When an account crosses a validated threshold:

```
OBSERVED COMPLEXITY
→ RECOMMENDED PLAN
→ BUSINESS VALUE EXPLANATION
→ OPTIONAL UPGRADE
```

The UI should explain why the capability is relevant.

---

## 7. Migration Safety

Plan migration must preserve:

- organization;
- branch identity;
- users;
- historical records;
- subscriptions;
- audit history.

---

## 8. Downgrade

Downgrade requires:

- entitlement check;
- impact preview;
- retention of inaccessible configuration/data according to contract;
- safe handling of over-limit entities.

Never silently delete data because a customer downgraded.

---

## 9. Expansion Revenue

Expansion can come from:

- plan change;
- branches;
- users;
- optional modules;
- integrations;
- support/SLA;
- implementation services.

Track each separately.

---

## 10. Contraction

Contraction may arise from:

- branch closure;
- staff reduction;
- seasonal business;
- plan downgrade.

Do not force customers to churn merely because their business temporarily shrinks.

---

## 11. Enterprise Expansion

Enterprise expansion is usually:

```
PILOT
→ MORE BRANCHES
→ MORE BUSINESS UNITS
→ MORE INTEGRATIONS
→ MORE GOVERNANCE
```

Expansion should be earned through successful delivery.

---

## 12. Upgrade Metrics

Track:

- trigger;
- recommended;
- accepted;
- rejected;
- time to upgrade;
- expansion MRR;
- retained post-upgrade;
- support change;
- contribution change.

---

## 13. Anti-Patterns

Reject:

- arbitrary feature locks;
- forced upgrade from inactivity;
- downgrade causing silent data deletion;
- device-based pricing as the main complexity measure;
- hiding why the upgrade matters.

---

## 14. Final Contract

```
MORE COMPLEX BUSINESS
→ MORE CONTROL
→ MORE VALUE
→ MORE APPROPRIATE COMMERCIAL PACKAGE
```
