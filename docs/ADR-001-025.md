## ADR Governance

These ADRs are binding architectural decisions unless superseded by a later ADR. They exist to prevent implementation drift, hidden architecture, accidental authority inversion, and contradictory subsystem designs.

Each ADR contains:

- Status
- Context
- Decision
- Decision details
- Alternatives considered
- Consequences
- Security implications
- Operational implications
- Testing implications
- Revisit triggers

### Status vocabulary

- **Accepted** — binding decision for implementation.
- **Accepted with constraints** — binding, but explicitly bounded by stated conditions.
- **Superseded** — replaced by a later ADR.
- **Proposed** — not yet binding.
- **Rejected** — explicitly considered and not selected.

### Change rule

An ADR is required when a change alters an architectural invariant, authority boundary, tenant/security model, financial semantics, offline semantics, integration trust model, or production deployment contract.

Routine refactoring that preserves externally observable behavior does not require a new ADR.

# ADR-001 — Rust-First Backend

**Status:** Accepted

## Context

Sitolo requires a backend capable of handling transactional business logic, concurrent requests, offline command ingestion, inventory races, financial state transitions, payment integration, tax integration, and potentially high concurrency without relying on unsafe memory management.

The backend must also have strong separation between transport, application orchestration, domain authority, persistence, and external integrations.

## Decision

Use **Rust as the primary backend implementation language**.

The primary runtime stack is:

```text
Rust
 ├── Tokio
 ├── Axum
 ├── SQLx
 ├── Serde
 ├── tracing / OpenTelemetry integration
 └── explicit domain/application/infrastructure boundaries
```

The approved Rust compiler/toolchain is pinned in `rust-toolchain.toml`. CI and release builders use the same pinned toolchain.

## Decision details

Domain code must not depend on Axum, SQLx, Redis clients, HTTP implementations, or cloud SDKs.

The conceptual structure remains:

```text
API
 ↓
Application
 ↓
Domain

Persistence / Providers
 ↕
Ports
```

## Alternatives considered

### TypeScript/Node.js
Rejected as the primary backend despite its strong developer experience because Rust better aligns with the project's long-term requirements around explicit ownership, memory safety, deterministic resource handling, and the user's Rust-first backend strategy.

### Java/Spring Boot
Rejected as the primary backend because the architecture does not require JVM-scale enterprise middleware and would add runtime/memory complexity that is unnecessary for the initial modular monolith.

### Go
Rejected because Rust provides stronger compile-time ownership guarantees and better alignment with the chosen backend strategy.

## Consequences

Positive:

- memory safety;
- predictable concurrency primitives;
- explicit error handling;
- strong type-level domain modelling;
- efficient resource usage;
- strong fit for workers and integration adapters.

Negative:

- steeper learning curve;
- smaller application-developer pool in some markets;
- slower initial implementation for developers unfamiliar with Rust;
- compile-time complexity can become a productivity problem if architectural boundaries are poorly designed.

## Security implications

Rust reduces memory-safety classes of defects but does not prevent authorization, cryptographic, business-logic, tenant-isolation, or insecure-configuration failures. Those remain explicit controls.

## Operational implications

The production artifact must include the exact compiler/toolchain and locked dependency state used to build it.

## Testing implications

Required baseline:

```text
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --workspace
cargo test --workspace --release
```

Additional property, integration, fuzz, and security tests are controlled by `testing_strategy.md`.

## Revisit triggers

Reconsider only if:

- the backend workload materially changes;
- organizational hiring constraints make the strategy unsustainable;
- a different language demonstrates substantially lower total risk without compromising architecture.

---

## Deep Implementation Dossier

### Architectural intent
This decision is not simply a language preference. It establishes the backend as the place where resource ownership, domain invariants, transaction boundaries, concurrency control and failure semantics are made explicit. The language choice is accepted because it supports those goals; the goals themselves remain the invariant.

### Required code boundaries
The repository must keep transport, application, domain and infrastructure concerns physically and logically distinguishable. Handlers parse requests and construct commands. Application services own orchestration and transaction scope. Domain modules own state transitions and invariant evaluation. Repositories persist authorized operations. Adapters isolate external protocols.

Forbidden dependency examples include domain imports of Axum types, SQLx row types, HTTP client errors, Redis APIs or provider payload structs. Provider DTOs must be mapped before entering the domain.

### Concurrency and failure analysis
Async execution must never turn an operation into an unbounded task. Every external I/O operation has a timeout/deadline. Worker concurrency is bounded. Database transactions are short. A cancellation must leave durable state in a recoverable condition. Rust's type system is used to make illegal states harder to express, but runtime authorization and business validation remain mandatory.

### Implementation evidence
A release candidate must demonstrate deterministic compilation from the pinned toolchain and lockfile, compile-time checked critical SQL where used, passing unit/integration/property tests, and dependency/security reports. Architecture tests should reject forbidden dependency edges.

### Rollback implication
Rollback means redeploying a previously verified artifact; it does not mean deleting business data or reversing external side effects. The code must preserve compatibility with the database migration state during rollback windows.

# ADR-002 — Flutter as Primary Mobile Client

**Status:** Accepted

## Context

The target market contains low-cost Android devices and unreliable connectivity. The client therefore needs local persistence, efficient UI, offline operation, synchronization, secure storage, and support for long-lived operational state.

## Decision

Use **Flutter as the primary mobile client**, with Android as the initial priority platform.

The mobile application must follow a layered architecture:

```text
UI
 ↓
Application state
 ↓
Domain commands
 ↓
Local persistence
 ↓
Synchronization
 ↓
API
```

## Alternatives considered

### Native Android/Kotlin
Rejected for the initial product because it increases platform-specific implementation cost when cross-platform delivery remains strategically useful.

### React Native
Rejected because Flutter provides a more tightly controlled UI/runtime model and the project's offline-first client architecture benefits from explicit native integration boundaries.

### Web/PWA only
Rejected because the product's offline and device integration requirements exceed what a web-only product should be expected to provide reliably across low-end hardware.

## Consequences

Positive:

- one primary mobile codebase;
- explicit local persistence capability;
- strong UI consistency;
- Android-first deployment.

Negative:

- larger binary/runtime than fully native minimal applications;
- platform-specific integration still exists;
- Flutter/Dart expertise is required.

## Security implications

Credentials and cryptographic material use OS-backed secure storage. The local SQLite database is treated as sensitive operational data and is minimized.

## Operational implications

The supported device matrix must include low/mid-range Android hardware, process death, storage pressure, battery pressure, network transitions, and app suspension.

## Revisit triggers

Reconsider only if a specific platform requirement cannot be satisfied safely and reliably with Flutter.

---

## Deep Implementation Dossier

### Operational model
Flutter is responsible for merchant-facing interaction and durable local continuity, not server authority. The mobile architecture must therefore model explicit states for authenticated, offline, syncing, conflicted, revoked and degraded operation. UI state must not be allowed to imply financial completion when the server has not accepted the command.

### Local trust boundary
The app should treat every value loaded from local storage as potentially stale. Server responses are validated before persistence. Sensitive cached data is minimized. Local migrations are version-controlled and tested under interrupted execution.

### Device lifecycle
Installation creates an independently tracked device identity. Logout, session expiry and device revocation are distinct events. A revoked device may display locally cached information subject to policy but cannot regain sensitive server authority without explicit re-enrollment.

### Performance contract
The implementation must measure memory, cold start, local query latency, checkout interaction latency, battery impact and sync throughput on representative low/mid-range Android hardware. Network transitions are a normal operating condition, not exceptional test cases.

### Evidence
The mobile release gate requires functional tests, synchronization tests, secure-storage verification, deep-link/navigation security checks and process-death recovery tests.

# ADR-003 — Tauri for Desktop

**Status:** Accepted

## Context

Some merchants require a desktop/back-office experience. The system already uses Rust extensively and wants a lighter native shell than a traditional heavyweight desktop runtime.

## Decision

Use **Tauri** for the desktop application, with Rust as the native capability layer and a constrained TypeScript UI.

## Constraints

Do not expose a generic shell, filesystem, eval, or unrestricted native bridge to the web UI.

Native commands must be narrow, explicit capabilities.

The server remains the business authorization boundary.

## Alternatives considered

### Electron
Rejected for the baseline because Tauri provides better alignment with the Rust backend strategy and avoids making an entire Chromium runtime the foundation of the desktop shell.

### Pure web application
Rejected for workflows where local device integration and desktop operational continuity are valuable.

### Native desktop per OS
Rejected for excessive maintenance and platform duplication in the initial architecture.

## Consequences

- smaller native integration surface;
- Rust reuse;
- more platform-specific testing than web-only delivery;
- careful capability design is mandatory.

## Revisit triggers

Reconsider if a desktop-native requirement appears that Tauri cannot meet safely or operationally.

---

## Deep Implementation Dossier

### Native capability model
Tauri is a capability boundary. Every Rust command exposed to the webview must have a narrow purpose and a typed input/output contract. Generic command execution, arbitrary filesystem traversal and arbitrary shell invocation are prohibited because they collapse the privilege boundary between UI content and the native host.

### Update trust
Desktop updates are security-sensitive. Update manifests, packages and signatures must be verified before installation. A failed or unverifiable update must not silently downgrade security controls.

### Testing
Test direct invocation of native commands without using the UI, malicious command arguments, unexpected navigation, local file access, developer/debug artifacts, source maps and update tampering. The security property is that bypassing the UI does not bypass the native boundary.

# ADR-004 — PostgreSQL as Server Authority

**Status:** Accepted

## Context

Sales, inventory, cash, payments, reconciliation, tenant state, authorization, audit and tax integration all require durable authoritative transactional state.

## Decision

**PostgreSQL is the authoritative server-side system of record.**

Application state may be projected into caches/read models, but no secondary store becomes authoritative for business truth.

## Required properties

- ACID transactions for atomic business operations;
- foreign keys;
- unique/check constraints;
- explicit transaction boundaries;
- least-privilege roles;
- TLS/private connectivity;
- backups/PITR appropriate to tier;
- RLS where it adds defense-in-depth value.

## Alternatives considered

### MongoDB/document-first authority
Rejected because Sitolo has strongly relational tenant, inventory, sales, payment, audit and reconciliation relationships and requires transactional constraints across these domains.

### Event store as sole authority
Rejected for initial architecture because it adds unnecessary operational complexity and would not automatically simplify queryability or authorization.

### Supabase as the application architecture
Supabase may be used as a managed PostgreSQL/infrastructure offering where operationally appropriate, but the domain remains PostgreSQL-centered. Supabase-specific APIs must not redefine core domain authority.

## Consequences

Positive:

- strong transaction semantics;
- relational integrity;
- mature ecosystem;
- excellent concurrency primitives;
- effective queryability.

Negative:

- careful indexing/schema engineering required;
- operational expertise required;
- large reporting workloads need bounded queries/read models.

## Security implications

Database roles are separated. Runtime roles must not become accidental schema owners or superusers. Tenant isolation is enforced in application logic and, where applicable, RLS.

## Revisit triggers

Only if sustained workload characteristics prove a different persistence architecture materially superior.

---

## Deep Implementation Dossier

### Authority contract
PostgreSQL is the canonical server-side store for transactional business state. A cache may accelerate reads; it may not be treated as a second write authority. Read models are disposable and rebuildable from authoritative state where their design requires.

### Transaction discipline
Critical operations such as finalizing a sale, posting an inventory movement, closing a cash session and recording a reconciliation decision must have an explicit transaction boundary. External HTTP calls do not occur inside those transactions.

### Database security
Runtime credentials are least-privilege and separate from migration ownership. Database endpoints remain private. RLS, where used, is tested under the actual runtime role. Statement, lock and transaction timeouts protect availability.

### Recovery
Backups, PITR and restore procedures must be tested, not assumed. A restored database must be validated against schema version, transaction counts, key invariants and external reconciliation state before being returned to service.

# ADR-005 — Modular Monolith First

**Status:** Accepted

## Context

Sitolo has multiple bounded contexts, but the early product requires transactional locality and low operational complexity. Splitting every context into a network service too early would create distributed consistency problems before the domain boundaries are proven.

## Decision

Implement the backend as a **modular monolith with workers and adapters**.

Conceptually:

```text
One deployable core
 ├── domain modules
 ├── application services
 ├── persistence
 ├── integration adapters
 └── workers
```

Module boundaries must be explicit so later service extraction remains possible.

## Alternatives considered

### Microservices-first
Rejected because it introduces network calls, distributed deployment, independent failure modes, service discovery, cross-service transactions, and operational overhead before those costs are justified.

### Monolithic without module boundaries
Rejected because it eventually becomes a shared-state codebase where business rules leak across contexts.

## Consequences

Positive:

- low operational complexity;
- local transactions;
- simpler debugging;
- fewer distributed failure modes;
- faster early iteration.

Negative:

- requires discipline;
- module boundaries can erode without code review;
- scaling individual domains independently is initially limited.

## Revisit triggers

Extraction should be considered when a module demonstrates a real independent scaling, reliability, regulatory, ownership, deployment, or security boundary.

---

## Deep Implementation Dossier

### Boundary discipline
A modular monolith is not permission to share everything. Each module should have explicit public application services and should avoid reaching directly into another module's persistence implementation. Cross-domain interactions should use commands, domain services, events or explicit application orchestration.

### Extraction readiness
A module is extraction-ready only when its owned data, events, authorization expectations, and external dependencies are understood. Service extraction should therefore be the consequence of a proven boundary rather than the method used to discover one.

### Operational benefit
One deployable core simplifies atomic business transactions, local debugging and incident response. The cost is that deployment and scaling are initially coarser-grained; worker classes and database resources can still be isolated where measured need exists.

# ADR-006 — Custom Domain-Aware Offline Synchronization

**Status:** Accepted

## Context

Generic replication and last-write-wins are unsafe for sales, inventory, payments, cash and financial corrections.

## Decision

Build a **Sitolo-specific, domain-aware offline command and synchronization protocol**.

Offline mutations are represented as durable commands with stable IDs and schema versions.

```text
local intent
 ↓
durable command
 ↓
sync transport
 ↓
auth/device/tenant checks
 ↓
idempotency
 ↓
domain validation
 ↓
transaction
 ↓
ack/conflict/reject/retry
```

## Key rule

> Offline capability provides continuity of operation, not permanent authority.

## Alternatives considered

### Last-write-wins
Rejected as unsafe for financial and stock state.

### Generic CRDT synchronization
Rejected for the core financial model because domain constraints such as stock availability, refund entitlement, approval and cash closure are not generic merge operations.

### Online-only
Rejected because intermittent connectivity is a core product constraint and offline continuity is a strategic product capability.

## Consequences

Positive:

- explicit conflict semantics;
- strong duplicate resistance;
- crash-safe command journal;
- bounded offline authority;
- reproducible forensic evidence.

Negative:

- substantial engineering complexity;
- protocol versioning becomes a long-lived compatibility responsibility.

## Revisit triggers

Only if a mature protocol can preserve all invariants and reduce total risk without losing domain semantics.

---

## Deep Implementation Dossier

### Command authority
The offline client records intent. The server re-evaluates identity, device state, tenant scope, authorization, idempotency and business invariants when the command is ingested. Local success must therefore be represented differently from authoritative server acceptance.

### Conflict taxonomy
The implementation must not invent generic merge semantics. Each mutation class declares whether it is mergeable, commutative, approval-bound, reject-and-refresh, or server-authoritative. Inventory, money and approval operations receive stricter handling than metadata edits.

### Protocol evolution
Commands, acknowledgements, errors and checkpoints are versioned. The server must reject unsupported schemas deterministically. New clients must remain interoperable with supported server versions during controlled rollout windows.

### Security
Replay, duplicate command IDs, modified payloads, revoked devices and checkpoint rollback are mandatory adversarial tests.

# ADR-007 — Transactional Outbox Before External Broker

**Status:** Accepted

## Context

Sitolo needs reliable publication of events/work items after successful transactions. A broker introduced too early would create an additional distributed system without solving the fundamental local atomicity problem.

## Decision

Use a **PostgreSQL transactional outbox** as the initial event/work publication mechanism.

The outbox row is inserted in the same transaction as the business state it describes.

```text
BEGIN
  business state
  audit
  outbox
COMMIT
```

Workers later claim/process the outbox item.

## Alternatives considered

### Kafka/RabbitMQ from day one
Rejected because the first reliability problem is transactional coupling between business state and publication, which the outbox directly addresses.

### In-memory events
Rejected because process crashes would lose work.

### Polling application tables directly
Rejected because it couples workers to mutable business state and makes event semantics ambiguous.

## Consequences

- simple initial architecture;
- durable event intent;
- replay capability;
- PostgreSQL becomes a temporary queue as well as a system of record.

The database-backed queue must still have bounded polling, indexing, leasing and retention.

## Revisit triggers

Introduce a dedicated broker only when measured throughput, isolation, fan-out, latency, or operational requirements justify it.

---

## Deep Implementation Dossier

### Atomic publication
The reason for the outbox is precise: the system must never reach a state where the business transaction commits but the durable intention to process its consequence disappears, or where the work is published for a transaction that rolled back.

### Delivery semantics
The implementation should assume at-least-once dispatch. Exactly-once end-to-end effects are achieved only where downstream operations are idempotent. The outbox itself may be processed more than once; consumers must detect prior application.

### Retention
Processed records require a deliberate retention/archival policy. Event history must not accidentally become an infinite queue. Queue tables need indexes that match claim/lease queries and bounded polling.

# ADR-008 — Scoped RBAC with Policy Predicates

**Status:** Accepted

## Context

Sitolo requires simple roles for common work but also branch/resource scopes, thresholds, state conditions and high-risk approvals.

A purely role-based model is too coarse; a generic policy language from day one is unnecessary.

## Decision

Use **scoped RBAC as the baseline**, augmented by strongly typed policy predicates for high-risk operations.

Authorization is conceptually:

```text
principal
+ tenant
+ scope
+ permission
+ resource
+ state
+ context
+ threshold
= decision
```

## Alternatives considered

### Simple role checks
Rejected because `is_manager == true` cannot safely express branch/resource/amount/state constraints.

### Full generic policy DSL
Rejected initially because it adds complexity before the policy vocabulary is sufficiently stable.

### Client-side policy
Rejected categorically.

## Consequences

Positive:

- understandable for merchants;
- strong server-side enforcement;
- easy negative testing;
- supports approval thresholds without creating a general-purpose policy language prematurely.

Negative:

- policy code requires discipline;
- future complexity may eventually require a more declarative policy engine.

## Revisit triggers

Revisit if policy complexity becomes difficult to express/test safely using strongly typed policy structures.

---

## Deep Implementation Dossier

### Policy structure
Permissions answer “what capability”; scope answers “where”; policy predicates answer “under what state/context/threshold.” This prevents a growing collection of ad-hoc boolean checks.

### High-risk actions
Refunds, role changes, MFA resets, payment credential changes, high-value adjustments and large exports may require step-up authentication or approval. Requester and approver identity are persisted as first-class evidence.

### Fail-closed behavior
If required policy context cannot be resolved, the sensitive operation is denied. Cached client policy is never sufficient to authorize a high-risk mutation.

### Test oracle
For each rule, tests cover allow, deny, boundary and bypass attempts. Removing a tenant or amount predicate in mutation testing must cause the security suite to fail.

# ADR-009 — Tenant Isolation as a Security Boundary

**Status:** Accepted

## Context

Sitolo is multi-tenant. A tenant data leak is a catastrophic security failure.

## Decision

Treat **organization/tenant isolation as a first-class security boundary** enforced at multiple layers:

```text
authenticated principal
 ↓
membership resolution
 ↓
application authorization
 ↓
repository scope
 ↓
database constraints/RLS where applicable
```

Client-provided tenant IDs are selectors, never proof of authority.

## Required invariant

A principal without active membership in tenant A must not read, mutate, export, reconcile, or otherwise exercise authority over tenant A.

## Alternatives considered

### Client-enforced tenant filtering
Rejected.

### URL-based tenant separation only
Rejected because routes are not security boundaries.

### Database-per-tenant only
Not selected for the initial architecture because it creates substantial provisioning, migration, backup and operational complexity. Dedicated databases remain a future enterprise isolation option.

## Consequences

Security testing becomes mandatory across every resource family.

## Revisit triggers

Revisit physical database isolation for enterprise customers when contractual, regulatory, or blast-radius requirements justify it.

---

## Deep Implementation Dossier

### Isolation layers
Tenant isolation must survive failure of any single convenience layer. A malformed route, forged object ID, stale client state or direct API call must not cross the tenant boundary because authorization, repository scope and database constraints remain independent defenses.

### Data modeling
Protected rows should carry direct tenant ownership where practical. This simplifies forensic queries, authorization predicates, partitioning options and constraint design.

### Operational response
Any credible cross-tenant exposure is a SEV-1 event. Response includes containment, credential/session review, evidence preservation, affected-tenant analysis, regression testing and post-incident control improvement.

# ADR-010 — Financial Immutability and Compensating Events

**Status:** Accepted

## Context

Historical sales, payment allocations, cash events, refunds and inventory movements must remain explainable. Destructive updates destroy evidence and can create reconciliation ambiguity.

## Decision

Finalized financial facts are **append-oriented and effectively immutable**.

Corrections are represented as explicit domain events:

```text
sale
 ↓
return
refund
reversal
adjustment
replacement
```

## Alternatives considered

### Mutable financial rows
Rejected.

### Event sourcing for every system object
Rejected because full event sourcing would add unnecessary complexity for non-financial configuration data.

### Audit log alone
Rejected because an audit entry cannot repair a contradictory authoritative state; the correction must itself be an authoritative domain fact.

## Consequences

Positive:

- reconstructability;
- auditability;
- safer reconciliation;
- strong fraud investigation support.

Negative:

- correction workflows are more complex;
- reporting requires understanding correction relationships.

## Revisit triggers

The immutability rule may only be weakened through an explicit ADR with legal/accounting evidence. The basic historical-truth principle is not optional.

---

## Deep Implementation Dossier

### Historical truth
Financial immutability means the system can always reconstruct the economic sequence. A correction references what it corrects and does not erase the original fact.

### API design
State-changing financial operations must be explicit commands. Generic PATCH or direct row mutation endpoints are prohibited for finalized financial state.

### Reporting
Reports must model both original and compensating events. A dashboard that reads only the latest mutable total is not an authoritative financial report.

### Fraud and audit
Corrections carry actor, reason, scope, timestamps and evidence. High-risk corrections may require approval and separation of duties.

# ADR-011 — Inventory as Immutable Ledger Plus Balance Projection

**Status:** Accepted

## Context

A single mutable quantity field cannot explain why stock changed and is unsafe under concurrent operations.

## Decision

Inventory is modeled as:

```text
immutable inventory movements
+
materialized balance projection
```

The ledger is evidence; the balance is an optimized current-state projection.

## Required concurrency rule

A stock decrement must atomically validate availability and post its corresponding inventory movement.

## Alternatives considered

### Mutable quantity only
Rejected.

### Full event sourcing of all catalogue/configuration state
Rejected as unnecessary.

### Application-memory locking
Rejected because multiple application instances do not share memory.

## Consequences

- stock history is reconstructable;
- balances can be repaired from movements;
- concurrent decrements require explicit DB-level concurrency controls.

## Revisit triggers

None for the core ledger principle. Projection implementation may evolve.

---

## Deep Implementation Dossier

### Ledger/projection split
The movement ledger is the explainable record of what happened. The balance is an optimization. If the projection becomes corrupt, it must be possible to rebuild it from authoritative movements.

### Concurrency
Stock availability is checked and consumed inside a single authoritative transaction or equivalent atomic database operation. Application-process mutexes are insufficient when multiple instances exist.

### Vertical dimensions
Lot, batch, expiry and inventory state are modeled only where product/vertical policy requires them. FEFO and quarantine behavior are domain policies, not accidental SQL ordering.

### Recovery
Projection repair tooling must detect mismatches between ledger-derived balance and stored balance without mutating the ledger.

# ADR-012 — Explicit Payment Intent / Attempt / Reconciliation Model

**Status:** Accepted

## Context

External payment systems can time out after committing. Webhooks can be duplicated or arrive late. The merchant's statement that a customer paid is not equivalent to provider evidence.

## Decision

Separate three concepts:

```text
PaymentIntent
   ↓
PaymentAttempt
   ↓
External/provider evidence
   ↓
Reconciliation
```

Payment state and sale state remain separate.

## Key rule

An external timeout creates an **unknown/pending** state rather than authorizing an unsafe blind retry.

## Alternatives considered

### Treat provider callback as final truth without reconciliation
Rejected.

### Make payment state part of the sale state machine
Rejected because a sale can exist while payment remains pending or partially settled.

### Client-controlled payment success
Rejected categorically.

## Consequences

- safer unknown-outcome handling;
- explicit reconciliation queue;
- more states and operational complexity.

## Revisit triggers

No change to the separation principle. Provider-specific capabilities may change by adapter.

---

## Deep Implementation Dossier

### Unknown outcome
The most dangerous payment failure is a timeout after the provider may have committed. The correct state is unknown/pending, followed by a status lookup or reconciliation path. Blind retry can create duplicate financial effects.

### Reconciliation model
Provider transaction references, amount, currency, merchant account and internal intent identity form the primary matching evidence. Heuristics may propose a match but must not silently close exceptions.

### Failure injection
Tests must simulate timeout-before-commit, timeout-after-commit, duplicate callbacks, late success, wrong amount, wrong account and refund replay.

# ADR-013 — External Integrations Behind Capability-Based Adapters

**Status:** Accepted

## Context

Payment providers, tax systems, notification systems and other external services have different APIs and capabilities.

Embedding provider-specific HTTP details in core business modules would couple the domain to external contracts.

## Decision

Create explicit adapter ports.

Examples:

```text
PaymentProvider
EisGateway
NotificationProvider
ObjectStorage
```

Each adapter declares supported capabilities and maps external concepts into canonical internal states.

## Alternatives considered

### Provider-specific logic in sales/payment modules
Rejected.

### One universal provider interface that pretends providers are identical
Rejected because missing provider capabilities must be explicit rather than emulated unsafely.

## Consequences

- provider changes are localized;
- integration contracts can be contract-tested independently;
- adapters become security-sensitive trust boundaries.

## Revisit triggers

Add or remove capabilities as provider evidence changes.

---

## Deep Implementation Dossier

### Adapter contract
Every external adapter implements canonical-to-provider mapping, provider-to-canonical mapping, authentication, timeout policy, error classification, idempotency strategy, telemetry and contract fixtures.

### Trust boundary
Provider responses are data, not commands. The application validates them against the expected intent and internal state before creating business effects.

### Provider capability differences
A missing capability causes a deterministic unsupported operation, not a hidden fallback with weaker guarantees. This makes provider behavior explicit and testable.

# ADR-014 — MRA EIS Is a Compliance Integration Boundary, Not Core Sale Authority

**Status:** Accepted with constraints

## Context

MRA EIS affects tax reporting/fiscalization, terminal configuration, offline operation and compliance evidence. However, temporary EIS failure must not corrupt the merchant's local business transaction.

## Decision

Treat MRA EIS as an **external compliance integration boundary**.

The local sale transaction remains authoritative for Sitolo's own commercial state. EIS reporting is a subsequent controlled integration state.

```text
local sale committed
 ↓
tax submission pending
 ↓
MRA interaction
 ├── accepted
 ├── retryable failure
 └── permanent rejection
```

The adapter owns:

- terminal lifecycle interactions;
- configuration refresh;
- sale submission;
- offline submission;
- response validation;
- external error mapping;
- MRA-specific signing/credential handling.

## Compliance constraint

Sitolo must not claim MRA production compliance/certification merely because API requests succeed. Current MRA requirements, terminal/product approval, production credentials, testing and certification evidence are release gates.

## Alternatives considered

### Make sale commit wait synchronously for MRA
Rejected because external availability would become a hard dependency for core local commerce.

### Ignore EIS until after launch
Rejected because tax/fiscalization requirements materially influence domain data and offline design.

### Put MRA HTTP calls throughout sales code
Rejected because it contaminates core domain logic with external protocol details.

## Consequences

Positive:

- core sales remain operational under integration degradation where legally/operationally permitted;
- integration can be retried;
- evidence is preserved.

Negative:

- tax state can temporarily diverge from local sale state;
- exception management is required;
- certification becomes a real operational gate.

## Revisit triggers

Any official change to MRA's API, terminal model, certification requirements, offline rules, or legally binding fiscalization behavior requires contract review and likely ADR update.

---

## Deep Implementation Dossier

### Local versus regulatory state
The local sale and the tax submission are separate state machines. A merchant transaction can be locally committed while tax submission is pending or rejected. Historical local financial facts must not be rewritten to imitate an external response.

### Terminal model
Terminal identity, activation, configuration version and MRA-issued operational constraints are integration state. They must be retained as snapshots/references sufficient to reconstruct which configuration governed a submission.

### Offline tax behavior
Sitolo's offline continuity policy and MRA's fiscal/offline policy are distinct. The stricter applicable rule wins for the relevant operation. No unsupported claim of compliance is permitted before MRA acceptance/certification evidence exists.

### Security
MRA-specific secrets and signing material remain isolated inside the integration boundary and never enter general sales code or client applications.

# ADR-015 — SQLite for Durable Mobile Operational State

**Status:** Accepted

## Context

Offline-first operation requires durable local state across network outages, app restarts, process death and device suspension.

## Decision

Use **SQLite as the local operational store** in the Flutter mobile application.

The local store contains only the minimum required data:

```text
product snapshots
price snapshots
stock views
sale drafts/committed local sales
command outbox
acknowledgements
sync checkpoints
local device state
audit evidence
```

## Alternatives considered

### Memory-only cache
Rejected because process death would destroy offline work.

### Key-value storage for all business data
Rejected because relational transactional semantics and queryability are needed.

### Full replicated PostgreSQL client
Rejected because it would dramatically increase local complexity and expose inappropriate server-side authority.

## Consequences

- durable offline operations;
- local migration responsibility;
- additional security exposure if device is compromised.

## Security constraints

Use platform-backed key protection/encryption mechanisms where practical, minimize cached data, and assume the device can be lost or compromised.

## Revisit triggers

The exact SQLite package/library remains an implementation choice and may be changed without changing this ADR's architectural decision.

---

## Deep Implementation Dossier

### Local transaction model
The local database must support atomic creation of offline commands and local business projections. A local sale is not “just a cache entry”; it is durable operational state that must survive process death.

### Storage limits
The design must account for low storage conditions, database growth, compaction/cleanup and corrupted/incomplete migrations. Cleanup cannot delete unsynced financial commands.

### Recovery
On application restart, the client reconstructs command state from durable rows rather than in-memory queues.

# ADR-016 — Server Authority Over Client Time

**Status:** Accepted

## Context

Offline devices need client timestamps for evidence and ordering, but device clocks can be wrong or maliciously changed.

## Decision

**Server time is authoritative for server-side security-sensitive decisions.**

Client time may be retained as evidence for offline operations but must not silently override:

- session expiry;
- authorization expiry;
- tax/security controls requiring server time;
- audit commit time;
- server-side financial ordering decisions where authoritative time is required.

## Alternatives considered

### Trust device timestamps
Rejected.

### Ignore client timestamps entirely
Rejected because offline forensic reconstruction benefits from preserving them.

## Consequences

The system needs both client and server timestamps in relevant offline records.

## Revisit triggers

Only for narrowly specified external protocols that define their own time semantics.

---

## Deep Implementation Dossier

### Timestamp semantics
Relevant records may hold client occurrence time, server receipt time and server commit time. The distinctions are essential for incident reconstruction and for proving that a manipulated device clock did not change authorization or financial authority.

### Clock abuse testing
Test future-dated, backdated and time-jumped devices. Client timestamps must not extend sessions, bypass policy windows or reorder authoritative server facts without an explicit domain rule.

# ADR-017 — Structured Domain Error Taxonomy

**Status:** Accepted

## Context

A single generic error type cannot distinguish invalid user input, authorization denial, concurrency conflict, duplicate commands, temporary provider outage, and permanent external rejection.

These states have different retry and UX semantics.

## Decision

Use a stable domain error taxonomy:

```text
ValidationError
AuthorizationDenied
ResourceNotFound
StateConflict
InvariantViolation
ConcurrencyConflict
IdempotencyConflict
InsufficientStock
PaymentReconciliationRequired
ExternalDependencyUnavailable
ExternalDependencyRejected
TaxSubmissionRejected
ApprovalRequired
FeatureNotEntitled
DeviceRevoked
```

Transport maps these to stable API problem responses. Internal storage/provider details remain diagnostic.

## Alternatives considered

### Raw database/provider errors
Rejected because they leak internal details and create unstable client behavior.

### HTTP status as the entire error model
Rejected because HTTP alone cannot encode sufficient domain semantics.

## Consequences

- predictable client behavior;
- explicit retry handling;
- stable API evolution.

## Revisit triggers

New domain semantics may add new error families. Existing meanings must not silently change.

---

## Deep Implementation Dossier

### Stable semantics
Error codes are part of the public contract. A client must be able to distinguish “try again,” “refresh,” “ask for approval,” “operation already happened,” and “permanently rejected.”

### Information disclosure
Internal SQL, stack traces, provider credentials and topology are diagnostic data, not API output. Public errors are safe and bounded.

### Backward compatibility
Error meanings must not silently change. New semantics add new codes or explicitly version behavior.

# ADR-018 — OAuth/OIDC-Aligned Authentication, Not Custom Cryptographic Protocols

**Status:** Accepted

## Context

Authentication is security-critical and involves password handling, sessions, tokens, MFA, recovery, key rotation and identity lifecycle.

## Decision

Use **standards-based authentication and authorization protocols**, preferring an established identity provider where commercial and residency constraints permit.

The application must not invent:

- password hashing algorithms;
- token formats;
- session cryptography;
- MFA cryptographic protocols;
- recovery token protocols.

The Rust backend validates trusted identity assertions and creates the application's authorization context.

## Alternatives considered

### Entire custom identity stack
Rejected due to unnecessary cryptographic and lifecycle risk.

### Purely trust an external token's role claims
Rejected because application-specific tenant/resource authorization remains Sitolo's responsibility.

## Consequences

- less custom security code;
- dependency on standards/provider lifecycle;
- provider selection remains an open implementation/commercial decision.

## Revisit triggers

Identity provider or self-hosted standards-auth implementation can change through an ADR as long as the security properties remain intact.

---

## Deep Implementation Dossier

### Identity versus authorization
An identity provider establishes who authenticated. Sitolo resolves membership, branch scope, permissions, state and business policy. External role claims cannot replace application authorization.

### Lifecycle
The system must handle token expiry, revocation, signing-key rotation, MFA, recovery and session invalidation without requiring application redeployment.

### Recovery
Account recovery is a high-risk workflow and must have anti-enumeration, rate-limiting, audit and abuse controls.

# ADR-019 — Device Identity Is Independent from User Identity

**Status:** Accepted

## Context

Offline operation and security response require the ability to revoke a device even if user credentials remain valid.

One device may have several users; one user may have several devices.

## Decision

Model devices as independent security/control-plane entities.

```text
User
Session
Device
```

are separate concepts linked by explicit relationships.

Device registration, authentication binding, revocation and replacement are explicit workflows.

## Alternatives considered

### Device = user credential
Rejected because device compromise cannot be independently contained.

### User-only authorization
Rejected because offline commands originate from a device context and lost-device response requires separate revocation.

## Consequences

- stronger containment;
- additional lifecycle state;
- device inventory and support operations become necessary.

## Revisit triggers

None for the separation principle.

---

## Deep Implementation Dossier

### Why device identity exists
Device state is a containment boundary. A stolen device should be revocable without disabling the user's other sessions. Conversely, a valid user session on a device must not implicitly authorize a revoked device to sync historical commands.

### Registration
Device registration establishes tenant association, device status, credential/key references, app version and last-seen state. Replacement is an explicit lifecycle operation.

### Testing
Direct API requests, delayed offline commands and replayed commands from a revoked device must all fail according to policy.

# ADR-020 — Workers Are First-Class Reliability Components

**Status:** Accepted

## Context

Payments, MRA EIS, exports, notifications, outbox delivery and synchronization maintenance cannot all be safely executed inline with user requests.

Workers themselves can crash, duplicate execution, lose connections, or encounter dependency outages.

## Decision

Use durable workers with:

```text
job ID
job type
payload
status
priority
attempt count
available_at
lease/lock state
worker ID
last error
completion timestamp
```

Workers are designed to be safely repeatable.

## Reliability rules

Every worker class has:

- bounded concurrency;
- timeout/deadline;
- retry budget;
- exponential backoff with jitter;
- dead-letter handling where appropriate;
- structured telemetry;
- lease recovery after worker crash.

## Alternatives considered

### Fire-and-forget background tasks inside API process
Rejected for durable financial work.

### Separate broker and consumer fleet immediately
Rejected as premature before the workload justifies it.

## Revisit triggers

Dedicated queue/broker architecture may be introduced when PostgreSQL-backed job execution becomes a measured bottleneck.

---

## Deep Implementation Dossier

### Worker semantics
Workers are durable state machines. Lease ownership, heartbeat, retry state and terminal completion must survive a process crash.

### Fairness
Financial/integration work gets protected capacity so reports or notifications cannot starve critical queues.

### Poison work
A job that repeatedly fails because its payload is invalid must become inspectable/quarantined rather than causing infinite retry amplification.

### Idempotency
A worker is considered correct when running it twice produces one business effect. External provider idempotency keys should be derived from stable internal operation identity where supported.

# ADR-021 — OpenTelemetry-Based Observability with Separate Audit Evidence

**Status:** Accepted

## Context

The platform needs distributed traces, structured logs and metrics for operations, but those signals must not become a substitute for authoritative business records.

## Decision

Use **OpenTelemetry** for application telemetry, with a controlled semantic-conventions version.

Keep three evidence categories distinct:

```text
Business truth      → domain/database records
Audit evidence      → immutable/restricted audit records
Operational telemetry → logs/metrics/traces
```

## Consequences

Positive:

- cross-service/request correlation;
- standard telemetry model;
- easier incident investigation.

Negative:

- cardinality management;
- privacy/redaction requirements;
- collector reliability becomes operationally important.

## Security constraints

Do not use telemetry labels containing unbounded user IDs, full payloads, tokens, secrets, or unnecessary PII.

## Alternatives considered

### Logging only
Rejected because logs do not provide efficient distributed latency/dependency analysis.

### Proprietary telemetry without standard model
Rejected for unnecessary coupling.

## Revisit triggers

Telemetry backend or collector implementation may change; the separation between telemetry and business truth may not.

---

## Deep Implementation Dossier

### Three evidence planes
Business truth, audit evidence and operational telemetry have different retention, integrity and availability properties. Combining them creates false assumptions about completeness.

### Cardinality
Metrics must use bounded dimensions. High-cardinality identifiers belong in traces/logs when justified, not as labels on every time series.

### Telemetry failure
Telemetry export must degrade independently. An observability outage must not make a normal sale impossible unless an explicitly documented safety requirement says otherwise.

### Audit integrity
Audit records must be protected against ordinary business-user mutation and retained according to governance requirements.

# ADR-022 — Security Gates Are Release-Blocking

**Status:** Accepted

## Context

Security controls that are merely advisory tend to be bypassed under deadline pressure.

Sitolo's threat surface includes tenant isolation, payments, offline synchronization, CI/CD, external integrations, and administrative operations.

## Decision

Critical security verification is **machine-enforced and release-blocking**.

Mandatory classes include:

```text
secrets
SAST/static analysis
SCA/dependency scanning
authentication
authorization
BOLA/tenant isolation
input/injection tests
web security
payment replay/verification
offline replay/revocation
CI supply-chain controls
resource limits
concurrency
DAST where applicable
restore/recovery gates
```

A scanner that failed to run is not equivalent to a passing scan.

## Alternatives considered

### Advisory security checks
Rejected.

### Manual security review only
Rejected as insufficient for regression prevention.

### Security-only pre-release milestone
Rejected because vulnerabilities can be introduced during ordinary development.

## Consequences

- slower merges when critical checks fail;
- stronger regression resistance;
- CI becomes production infrastructure and must itself be secured.

## Revisit triggers

Thresholds and individual tooling may evolve. The release-blocking principle remains.

---

## Deep Implementation Dossier

### Gate semantics
The CI system distinguishes PASS from NOT RUN. Scanner crashes, missing credentials, network failures or empty reports are failures of verification, not security passes.

### Change control
Security gates themselves are production infrastructure. Changes to workflows, permissions, action versions, secret access or bypass mechanisms receive security review.

### Exception policy
Emergency exceptions require owner, scope, expiry, compensating controls and retrospective review. Exceptions cannot silently disable tenant isolation, financial integrity or credential controls.

# ADR-023 — No Arbitrary Microservices, Kubernetes, or Broker Before Evidence

**Status:** Accepted

## Context

The word “enterprise” often triggers premature adoption of large infrastructure stacks.

Sitolo instead requires reliability, security, scalability and recovery that can be delivered with simpler architecture during early stages.

## Decision

Do not adopt:

- microservices;
- Kubernetes;
- Kafka/RabbitMQ;
- distributed transactions;
- service mesh;
- multi-region active-active;

until a measurable requirement justifies the added operational complexity.

These remain valid future options.

## Alternatives considered

### Kubernetes-first platform
Rejected because it creates a substantial control plane and security/operations surface that does not itself create merchant correctness.

### Microservices-first
Rejected by ADR-005.

### Managed serverless-only architecture
Not selected as the universal baseline because long-lived workers, database transaction control and offline synchronization benefit from explicit runtime control. Individual services may still use managed infrastructure where appropriate.

## Consequences

- lower initial infrastructure complexity;
- easier debugging;
- less independent scaling at first;
- future extraction requires maintaining good module boundaries.

## Revisit criteria

Adoption requires a written decision showing one or more of:

```text
measured bottleneck
independent scaling requirement
security isolation requirement
regulatory boundary
operational ownership boundary
availability requirement
```

Not “enterprise architecture” as a standalone justification.

---

## Deep Implementation Dossier

### Evidence threshold
Infrastructure complexity is justified by measured need. The request must identify the bottleneck or isolation requirement, quantify impact, explain failure modes introduced, and define migration/recovery.

### Hidden costs
Every new service adds network paths, credentials, deployments, logs, policies, failure modes and patching obligations. The decision process must account for those costs rather than comparing only runtime throughput.

### Future migration
Module boundaries, event contracts and stable APIs are the preparation for future decomposition. Premature decomposition is not the preparation.

# ADR-024 — Reproducible, Traceable Production Artifacts

**Status:** Accepted

## Context

A production system cannot be secured reliably if binaries, containers and dependencies cannot be traced back to source and build inputs.

The repository has previously encountered dependency/toolchain alignment problems, making deterministic build state especially important.

## Decision

Every production artifact must be traceable to:

```text
source commit
Rust toolchain
locked dependencies
build environment
configuration class
artifact digest
SBOM
provenance/attestation
```

Dependencies must be locked and controlled.

Release artifacts should be signed and verified before deployment.

## Required controls

- `Cargo.lock` committed for application binaries;
- exact Rust toolchain pin;
- frontend lockfiles;
- container image digest pinning for deployment references where practical;
- SBOM generation;
- provenance generation;
- artifact verification;
- CI identity least privilege.

## Alternatives considered

### Build from moving dependency versions
Rejected because it destroys reproducibility.

### Manual server builds
Rejected because the result cannot be reliably reproduced or audited.

### “Latest stable” toolchain in CI
Rejected because it allows unreviewed compiler behavior changes.

## Consequences

- stronger supply-chain accountability;
- more dependency maintenance work;
- release pipeline becomes more sophisticated.

## Revisit triggers

Supply-chain tooling may evolve while the principle of traceable immutable builds remains.

---

## Deep Implementation Dossier

### Release identity
A production artifact is a cryptographically identifiable object, not merely a version string. The artifact digest is linked to source commit, compiler/toolchain, dependencies, build environment, SBOM and provenance.

### Builder trust
CI identities that can produce production artifacts are high-value credentials. Their permissions, environments and secret access must be minimized and audited.

### Rebuild test
A maturity test is the ability to explain and reproduce a released artifact without relying on an engineer's workstation.

# ADR-025 — Explicit Failure, Recovery, and Release-Evidence Model

**Status:** Accepted

## Context

Sitolo operates in an environment containing network outages, lost devices, provider failures, database incidents, staff error/fraud, duplicate callbacks, synchronization conflicts, and external compliance dependencies.

Functional correctness alone cannot establish production readiness.

## Decision

Every critical capability must define:

```text
happy path
failure states
retry semantics
idempotency semantics
recovery procedure
audit evidence
telemetry
negative tests
release evidence
```

The system therefore treats:

```text
DETECT
 → CONTAIN
 → PRESERVE EVIDENCE
 → RECOVER
 → VERIFY
 → REGRESSION TEST
 → IMPROVE CONTROL
```

as an engineering lifecycle.

## Release evidence categories

A production release must be supported by evidence covering:

```text
Architecture
Security
Domain correctness
Database integrity
API contracts
Authentication/authorization
Offline behavior
Payments
MRA EIS
Observability
Deployment
Backup/restore
Supply chain
Operational readiness
```

## Alternatives considered

### Feature-complete = production-ready
Rejected.

### Manual QA sign-off only
Rejected because many critical properties require machine-enforced verification and failure injection.

### Runbooks as prose only
Rejected. High-impact runbooks must contain actionable commands/procedures, ownership, escalation and verification steps.

## Consequences

Positive:

- production readiness becomes measurable;
- incidents feed back into engineering;
- recovery is tested rather than assumed.

Negative:

- larger release process;
- operational evidence takes time to produce;
- teams must maintain test fixtures and runbooks as code-adjacent artifacts.

## Revisit triggers

The specific evidence forms and tooling can evolve. The principle that production readiness requires evidence is permanent.

# Architectural Invariants Protected by the ADR Set

The following invariants are cross-cutting and cannot be violated by local implementation convenience:

```text
1. PostgreSQL is authoritative for server-side business truth.
2. Clients are not authority merely because they are online or offline.
3. Tenant membership is derived from trusted server-side state.
4. Authorization is server-enforced.
5. Device identity is independently revocable.
6. Finalized financial facts are not destructively rewritten.
7. Inventory history is ledger-backed.
8. Financial operations are idempotent where retries can occur.
9. External side effects are never hidden inside long-lived database transactions.
10. External providers are trust boundaries and must be reconciled.
11. Offline synchronization is domain-aware, not generic last-write-wins.
12. Security checks are release-blocking.
13. Production artifacts are reproducible and traceable.
14. Failures must have explicit states and recovery paths.
15. Observability is evidence about behavior, not a competing business authority.
16. Enterprise complexity must be justified by measured requirements.
17. Historical truth must survive schema, pricing, policy and provider evolution.
18. No secret belongs in client applications, source, logs, telemetry, or public artifacts.
19. High-risk administrative access is separately controlled and audited.
20. Regulatory compliance is demonstrated by evidence, not asserted from API connectivity.
```
